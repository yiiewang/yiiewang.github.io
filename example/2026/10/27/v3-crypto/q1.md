## 一、先有一个大图景：证书解决什么问题

网络通信有三个基本问题：

| 问题 | 例子 | 手段 |
|---|---|---|
| 机密性 | 中间人能看到我发的消息 | 加密（对称加密） |
| 完整性 | 消息被改了我不知道 | 哈希 + 签名 |
| 身份认证 | 和我说话的到底是不是真的服务器 | 证书（核心） |

**证书本质上就是一张"带官方盖章的身份证"，证明"这个公钥确实属于 minibridge-demo-ca 这个主体"。**

## 二、密钥对：公钥和私钥

非对称加密生成一对数学上绑定的密钥：

- **私钥**：只能自己藏着（`ca.key`）。能"签名"。
- **公钥**：可以随便公开（就嵌在 `ca.crt` 里）。能"验证签名"。

关键性质：
- 用私钥签的东西，任何人拿公钥都能验——**证明"确实是私钥持有者签的"**。
- 反过来不行：拿公钥推不出私钥。

```
私钥  --签名-->  签名值
公钥  --验证-->  签名值 ✓/✗
```

你的 `ca.key` 是 **EC（椭圆曲线）** 密钥，曲线 `prime256v1`（也叫 P-256、secp256r1）。不用管数学，只要知道：它比 RSA 短得多（256 位 vs 2048 位），速度也快，现在主流都在用它。

> 为什么 `04:36:ed:...` 那一串是公钥？`04` 表示"未压缩格式"，后面 32 字节是 X 坐标、32 字节是 Y 坐标，合起来就是椭圆曲线上的一个点，也就是公钥。

## 三、签名到底是什么

直接对整份文件签名太慢，所以流程是：

```
原始内容 --哈希--> 摘要（固定长度，比如 SHA-256 = 32 字节）
摘要    --私钥加密--> 签名值
```

验证时反过来：对内容重新哈希，用公钥解开签名值，两个摘要一样 → 内容没被改过，且确实是私钥持有者签的。

所以 `ecdsa-with-SHA256` 拆开读就是：
- `SHA256` = 哈希算法
- `ecdsa` = 用 EC 私钥做签名

## 四、X.509 证书的结构

证书（`.crt`）就是一个格式化文件，里面装了这些东西：

```
证书 = {
    谁的身份（Subject）        : CN=minibridge-demo-ca
    这个人的公钥               : 04:36:ed:...
    有效期                     : 2026-10-29 ~ 2027-10-29
    签发者是谁（Issuer）        : CN=minibridge-demo-ca
    一些用途限制（扩展）        : 可以做 CA、只能签证书
    签发者用私钥做的签名        : 30:46:02:21:...
}
```

**核心理解：证书 = 公钥 + 身份信息 + 别人的签名。**

## 五、CA 和"自签名"

问题来了：谁来给"身份证"盖章？

现实世界：公安局给你发身份证，你信任公安局。
数字世界：**CA（Certificate Authority）** 给服务器发证书，你信任 CA。

那 CA 自己的身份证谁发？

- **自签名（Self-signed）**：自己给自己签。你的 `ca.crt` 就是这样——`Issuer` 和 `Subject` 完全一样，都是 `minibridge-demo-ca`。
- 这是信任链的**根**。根 CA 被你"无条件信任"（因为是你自己生成的、手动装进信任列表的）。

**你这套 demo 的信任结构：**

```
ca.crt (根 CA，自签名，你手动信任)
 ├── srv.crt  (服务端证书，由 ca.key 签发，客户端校验它)
 └── cli.crt  (客户端证书，由 ca.key 签发，服务端校验它)
```

这就是 **mTLS（双向 TLS）**：不只有服务器证明自己，客户端也要出示证书。

## 六、扩展（Extensions）为什么重要

扩展是 v3 证书才有的一堆"用途标签"，防止证书被滥用：

| 扩展 | 你的值 | 含义 |
|---|---|---|
| `basicConstraints` | `CA:TRUE` | **关键**：允许它给别的证书签名。普通服务器证书这里是 `CA:FALSE` |
| `keyUsage` | `Certificate Sign, CRL Sign` | 这个密钥只允许做这两件事，不能拿去做 TLS 握手加密 |
| `subjectKeyIdentifier` | `1F:F0:...` | 这张证书的"编号"，方便别人引用它（比如子证书说"我爸是 1F:F0:..."） |

`critical` 的意思是：验证方如果不认识这个扩展，**必须拒绝这张证书**，不能忽略。

## 七、把 ca.crt 的输出重新读一遍

| 你看到的 | 一句话解释 |
|---|---|
| `Version: 3` | 带扩展的新版格式 |
| `Serial Number` | 证书的流水号，理论上唯一 |
| `Signature Algorithm: ecdsa-with-SHA256` | 用 EC 私钥 + SHA256 哈希签的名 |
| `Issuer` | 签发者（这里是自己） |
| `Subject` | 这张证书属于谁 |
| `Validity` | 有效期，过期就不被信任 |
| `Public-Key: (256 bit)` | 证书里公开的公钥 |
| `prime256v1 / P-256` | 用的椭圆曲线 |
| `Basic Constraints: CA:TRUE` | 它是 CA，能签别人 |
| `Key Usage` | 只能签证书、签吊销列表 |
| `Subject Key Identifier` | 它的编号 |
| 末尾 `30:46:02:21:...` | 真正的签名值（ECDSA 的 r 和 s 两个数） |

## 八、放进 TLS 握手看一眼（最简版）

客户端连服务器时：

1. 服务器发来 `srv.crt`。
2. 客户端检查：这证书是不是我信任的 CA 签的？→ 用 `ca.crt` 里的公钥去验 `srv.crt` 的签名。
3. 验过 → 确认"我连的确实是持有 `srv.key` 的那台服务器"。
4. 双方用非对称加密协商出一个**临时的对称密钥**，之后通信全用对称加密（快）。

你的 demo 里多一步：服务器也要求客户端出示 `cli.crt`，用同一个 `ca.crt` 验一遍。这就是 mTLS。
