# 实用 Agent 学习路线（个人定制版）

> 目标：6 个半天，做出一个**你每天真的会用的 agent**——前半程是「每日简报」流程自动化，
> 后半程给它加上领域知识库，合成为一个既有流程又有大脑的完整 agent。
>
> 技术栈：Go + OpenAI 兼容接口（base_url + apikey）。
> 节奏：每次半天（约 4 小时），做完一个里程碑再进下一个。

## 全程贯穿的三条铁律

1. **apikey 永远从环境变量读**，不写进代码、不提交到仓库（.gitignore 提前加）
2. **每个里程碑的产物必须能跑**：一条命令，看到输出。跑不起来的阶段不算完成
3. **每次模型干了蠢事，记一条「蠢事集」**（格式：现象 → 定位 → 方案 → 数据），这是面试和复盘的硬通货

## 里程碑总览

| # | 半天主题 | 产物 | 核心能力 |
|---|---|---|---|
| M1 | 第一次对话 | `briefing` CLI：长文 → 结构化摘要 | API 调用、prompt、参数、流式 |
| M2 | 第一双手 | 模型通过 function calling 调你的工具 | 工具 schema、参数校验 |
| M3 | 固定流程 | 一条命令生成当日简报，全自动 | agent loop、终止控制、dry-run |
| M4 | 领域大脑 | agent 能检索你的文档并引用回答 | 检索、上下文工程、token 成本 |
| M5 | 知道它靠不靠谱 | 评测报告：成功率/轮数/成本 | 评测集、trace、回归对比 |
| M6 | 每天真的在用 | 稳定服务：重试/超时/日志/定时 | 生产化、失败处理、审计 |

## M1 第一次对话（~4h）

**产物**：`briefing` CLI——输入一个文本文件，输出格式稳定的结构化摘要。

**时间分解**：

| 时段 | 做什么 |
|---|---|
| 1h | Go 项目初始化 + 用 `net/http` 手写第一个 `/chat/completions` 请求（不引 SDK，一个 POST 就够，手写一遍永远懂协议） |
| 1.5h | 结构化输出：system prompt 约定 JSON 格式，解析模型返回 |
| 1h | CLI 化：`go run . <文件路径>`，输出存为 markdown |
| 0.5h | 玩参数：对比 temperature 0 vs 1、换 system prompt，观察行为差异（记入蠢事集或惊喜集） |

**知识点**：messages 三角色（system/user/assistant）、temperature、max_tokens、
流式（stream: true）与非流式的区别、JSON 输出的稳定性问题。

**验收**：喂 3 篇不同长度的文章，摘要格式完全一致；apikey 硬编码检查为零。

**常见坑**：模型返回的 JSON 带 markdown 代码围栏；忘记设置 Content-Type；
中文 token 计数比英文贵（观察 usage 字段）。

## M2 第一双手（~4h）

**产物**：agent 拥有 2 个工具（`list_dir`、`read_file`），模型自主决定调用。

**时间分解**：

| 时段 | 做什么 |
|---|---|
| 1h | 定义第一个工具 schema，跑通「模型返回 tool_calls → 你执行 → 结果喂回去 → 模型给最终回答」 |
| 1.5h | 加第二个工具；模型开始选错工具/编参数，记蠢事 |
| 1h | 参数校验层：工具执行前先校验，非法参数把错误信息返回给模型让它自纠 |
| 0.5h | 对比：同一个问题，工具描述改一个词，行为怎么变 |

**知识点**：`tools`/`tool_choice`/`tool_calls` 协议、工具描述怎么写模型才不编、
工具结果的角色（tool message）、错误回传设计。

**验收**：问「xx 目录下有什么」，模型通过工具回答而非瞎编；构造一个非法路径，
模型能根据错误信息自我纠正至少一次。

**常见坑**：工具描述太模糊导致模型该调不调；把校验错误直接 panic 而不是返回给模型。

## M3 固定流程（~4h）

**产物**：一条命令生成当日简报：收集（工具）→ 写稿（模型）→ 落盘（工具）→ 复查（工具）→ 结束。

**时间分解**：

| 时段 | 做什么 |
|---|---|
| 1.5h | 把 M2 的单轮工具调用改成 loop：模型反复调工具直到给最终答案 |
| 1h | 终止控制三件套：最大轮数、收敛检测、重复检测（连续两轮调同一工具同一参数 = 报警） |
| 1h | 安全边界：所有写操作默认 dry-run，加 `--apply` 才真写 |
| 0.5h | 故意制造死循环（prompt 里诱导），验证防护生效，记入蠢事集 |

**知识点**：agent loop 状态机、不动点/收敛、幂等、写操作安全。

**验收**：全自动生成一份简报文件；人为诱导死循环时程序安全退出且打印原因；
不加 `--apply` 时磁盘零改动。

**常见坑**：没有重复检测，模型对着同一个文件反复读取直到 max rounds；
写文件不加锁，并发跑两个实例互相覆盖。

## M4 领域大脑（~4h）

**产物**：知识库问答——你的专业文档可被 agent 检索，回答带出处。

**时间分解**：

| 时段 | 做什么 |
|---|---|
| 1h | 文档入库：切分（按标题/段落），存为本地 JSON 索引 |
| 1.5h | 实现 `search_kb` 工具：先做关键词检索（BM25 或简单评分），跑通「问题 → 检索 → 引用回答」 |
| 1h | 上下文工程：检索结果喂多少条、每条截多长；打印每次请求的 token 数 |
| 0.5h | 实验：检索 top3 vs top10，回答质量和成本的变化 |

**知识点**：文档切分、检索评分、上下文预算、前缀缓存（system prompt 不变可命中缓存）。

**验收**：问 5 个领域问题，回答引用你的文档原文；一次问答的成本（token 数）可打印。

**常见坑**：检索结果整段塞进 prompt 导致超限；切分太碎，单块没有完整语义。

## M5 知道它靠不靠谱（~4h）

**产物**：评测报告——你的 agent 的成功率、平均轮数、单次成本三个数字，改动能看到 before/after。

**时间分解**：

| 时段 | 做什么 |
|---|---|
| 1.5h | 造评测集：20-50 条真实问题 + 期望要点（golden set） |
| 1h | trace 记录：每轮对话落盘成 JSONL，可回放 |
| 1h | 跑评测：统计三指标；对比「改 prompt 前 vs 后」 |
| 0.5h | 用 LLM 当裁判给回答打分，同时人工抽查它的误判 |

**知识点**：golden set 构造、确定性回归（temperature=0 也不完全稳怎么办）、LLM-as-judge 的适用与失效。

**验收**：一句可量化的话：「我的 agent 在 50 条评测集上成功率 X%，平均 Y 轮，单次 Z token」。

**常见坑**：评测集只有简单问题，全是满分没有区分度；judge 模型偏爱吃长回答。

## M6 每天真的在用（~4h）

**产物**：稳定运行的日常服务：定时生成简报、失败自动重试、全程留痕。

**时间分解**：

| 时段 | 做什么 |
|---|---|
| 1h | 网络层健壮性：超时（context）、重试（指数退避）、限流处理 |
| 1h | 审计日志：谁在何时、花了多少 token、调了什么工具、改了什么文件 |
| 1h | 定时化：cron / systemd timer 每天自动跑，结果落盘或发送 |
| 1h | 破坏性测试：断网、坏 apikey、知识库文件损坏——程序不挂死且日志可查因 |

**知识点**：context 超时与取消、指数退避、幂等重试、审计设计。

**验收**：连续运行 7 天不挂；人为注错（断网/坏 key）不 panic 且能自恢复；
任何一天的简报都能从日志还原当时发生了什么。

---

## 完成后的三个资产

1. **一个天天在用的 agent**（流程 + 知识库 + 评测 + 观测的完整作品）
2. **一份蠢事集**（每个坑都是面试故事：现象 → 定位 → 方案 → 数据）
3. **三个数字**（成功率 / 轮数 / 成本）——敢说「我的 agent 靠谱」的依据
