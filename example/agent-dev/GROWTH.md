# Agent 开发工程师成长路线：从「会调 API」到「能对 agent 的行为负责」

配套项目：`example/minibridge/agent-runtime`（已长出 check / fix 两步，本路线的后续阶段都在它上面继续长）。
本文管三件事：**agent 工程师的能力地图、按什么顺序学、学完在市场上值多少**。

---

## 0. 最重要的一条方法论（先记住这个）

> Agent 开发的面试考的不是「调过哪个模型的 API」，而是：**你的 agent 为什么不靠谱、你怎么知道它不靠谱、你为此做了什么**。
> 每个阶段都要能讲成故事：现象（agent 干了什么蠢事）→ 定位（哪层的问题：prompt / 工具设计 / 循环控制）→ 方案 → 权衡 → 数据。

### 故事模板

```
功能：<agent 的哪块能力>
现象：<agent 实际干出的错事，越具体越好>
定位：<怎么发现是这一层的 —— 看 trace？回放对话？打点？>
方案：<怎么改的：改了 prompt / 改了工具签名 / 加了终止条件>
权衡：<为什么选它、放弃了什么>
数据：<改动前后成功率 / 成本 / 轮数对比>
```

### agent 线最容易攒到的真实踩坑素材（自己撞一遍就有）

| 坑 | 可讲的点 |
|---|---|
| agent 死循环：反复调同一个工具 | 循环终止条件、重复检测、预算控制 |
| 模型把工具参数编错（幻觉出字段/值） | 工具 schema 设计、参数校验层 |
| 上下文塞爆：长任务后期模型「失忆」 | 上下文管理、摘要压缩、状态外置 |
| 模型该调工具时瞎答、该答时瞎调 | prompt 结构、few-shot、模型选型 |
| 一次 agent run 花了几十块 token 费 | 成本观测、缓存、小模型路由 |
| 「看起来对了」但没法回归 | 评测集、成功率统计、trace 回放 |

## 1. 这批能力的画像

> 能独立交付一个「行为可解释、结果可验证、成本可控制」的 agent 应用：
> 循环设计 → 工具协议 → 上下文工程 → 评测 → 上线观测，全流程自己扛。

这不是「会拼 prompt」那一层。**「会用框架（LangChain 等）搭 demo」和「能对 agent 行为负责」之间隔着一整个评测与控制层**，市场为后者付钱。

## 2. 含金量分布不均（很重要）

| 值钱 | 不太值钱 |
|---|---|
| Agent loop 的设计与收敛控制 | 会调某家的 chat API |
| 工具/函数调用的 schema 设计与校验 | 会用某个 agent 框架的链式语法 |
| 上下文工程：什么进 prompt、什么外置 | prompt 技巧本身（角色扮演、思维链模板） |
| 评测体系：怎么证明你的 agent 靠谱 | 接了多少个模型、做了多少个 demo |
| 成本与延迟的量化优化 | 「用了 RAG/多智能体」这类名词堆砌 |

一句话：**模型能力是平台的，可靠性是你的。** 前者会随版本升级贬值，后者不会。

## 3. 学习路线（核心节，按序执行）

每个阶段一个可运行产物，全部长在 `agent-runtime` 上。跳序的代价：没做 1~2 就接模型，你只会得到「模型偶尔对了但不知道为什么」的 demo。

| 阶段 | 目录（规划） | 学什么 | 验收标准 |
|---|---|---|---|
| s0 提取 | `baseline`（已完成） | 感知：把文件变成结构化数据 | 能列出全部链接及行号 |
| s1 判断 | `check`（已完成） | 确定性决策：规则层不花钱、可测试 | 空文字/坏目标/重复全部命中 |
| s2 动作 | `fix`（已完成） | 写操作与安全边界：默认 dry-run | `-fix` 只改该改的行 |
| s3 循环 | `v1-loop` | **agent loop**：修完重查直到收敛；终止条件、最大轮数、防死循环 | 首轮 2 问题 → 修 → 复查 0 问题 → 自动退出 |
| s4 决策换模型 | `v2-llm` | function calling：把 check/fix 包成工具给模型（混元/OpenAI 兼容接口），模型自主决定下一步 | 同一输入，模型能自己走到收敛 |
| s5 上下文工程 | `v3-ctx` | 检查结果怎么喂（全量/摘要/差量）、状态外置、token 成本测量 | 10 倍大的文件下成本可控、行为不劣化 |
| s6 评测 | `v4-eval` | 评测集、成功率/轮数/成本三个指标、trace 回放 | 有 before/after 数字，能回归 |
| s7 生产化 | `v5-ops` | 失败重试、超时、并发安全（写文件加锁）、审计日志 | 故意注错不挂死，全程可观测 |

前三步已完成的共同点：**不碰模型，先把「工具→判断→动作」的骨架做对**。模型进来时只替换「判断」那一格，骨架不动——这就是 agent 架构最重要的分层意识。

### 每一步对应的知识点清单（自用查漏）

- s3：状态机思维；不动点/收敛；幂等（修过的再修一遍不能坏事）
- s4：OpenAI 兼容协议（`tools`/`tool_choice`/`tool_calls`）；工具描述写法；参数校验在谁那层做
- s5：token 预算；结构化摘要；外部状态 vs 对话历史；缓存（前缀不变可命中）
- s6：golden set 怎么造；确定性回归（temperature=0 也不完全稳，怎么办）；LLM-as-judge 的适用与失效
- s7：超时与取消（context）；文件锁/乐观并发；费率与限流；审计（谁在何时改了哪个文件）

## 4. 职级与薪资（2024-2026 中国，AI 应用方向，粗区间）

| 档 | 大致定位 | 一线年包（税前） |
|---|---|---|
| 初级（L2-L3） | 会接 API、能搭 RAG/agent demo | 25–40 万 |
| 高级（P6/2-1） | 独立负责一个 agent 应用含评测 | 35–55 万 |
| 资深（P7/2-2） | 定团队的 agent 平台/工具链选型与规范 | 55–85 万 |

同样的三条免责：行情波动大；年包口径混乱；真实数字看脉脉/OfferShow/levels.fyi 近半年同城同档。

**一个 agent 线特有的现实**：这个方向 2024 年后才起量，评级体系不成熟——有的厂把它当普通后端（不吃香），有的当 AI 核心（溢价高）。**面之前先搞清楚对方团队靠 agent 赚钱还是烧钱**，前者才是溢价岗。

## 5. 从「学完路线」到「那个级别」差三件事

1. **真实负载**：demo 文件 100 行 vs 生产每天跑 10 万次、文件几 MB——退化模式完全不同（成本、上下文、并发）
2. **协作**：模型选型要过评审、工具 schema 是团队契约、prompt 变更要被人 review
3. **事故**：「agent 批量改坏了 30 个文件」这种事故的定位与止损，是 P7 面试的硬通货

## 6. 坐标：用「能解决什么层级的问题」丈量

| 层 | 能解决什么 | 现状 |
|---|---|---|
| L1 | 会调模型 API | 已过 |
| L2 | 能搭出一个能跑的 agent demo | s0-s2 已具备 |
| L3 | **能加控制层让 agent 可靠收敛** | **当前位置（s3 起点）** |
| L4 | 有评测体系，敢说「我的 agent 成功率 X%」 | s6 后 |
| L5 | 定团队规范：工具怎么设计、评测怎么建 | 对应 P7 |
| L6 | 决定业务里哪些场景该上 agent、哪些不该 | 业务负责人 |

## 7. 再往上的四条路

**① 深度**：上下文工程与成本——长任务不退化、token 成本可预测。产物是数字：上下文压缩前后成本曲线、不同模型的任务成功率对比。

**② 系统**：多 agent 协作（规划者+执行者+审查者）、状态共享、部分失败恢复。经典跃迁是**做一个多角色 agent 管道并处理「中间某步失败」**——单 agent 永远遇不到的难题。

**③ 决策**：给开源 agent 框架/工具库提 PR（它们的 issue 区是现成的需求池）；在公司内定 agent 开发规范。

**④ 杠杆**：把 agent 从「个人工具」变成「团队依赖的服务」——谁在用、省了多少人时、出错率多少，这是从技术到结果的跃迁。

## 8. 见效最快的两件事

1. **把 agent-runtime 走完全部 7 个阶段并写成博客**：一个从 40 行种子长成带评测与观测的完整 agent 的连载，就是最硬的作品集
2. **建一个「agent 蠢事集」**：每次 agent 干蠢事，按第 0 节模板记一条。攒够 10 条，面试随便问

## 9. 自检清单（答得出来才算真到位）

- [ ] 白板画 agent loop 状态机，说清终止条件至少要防哪三种死循环
- [ ] 不看文档设计一个工具 schema：参数怎么描述模型才不编错、错误怎么返回给模型让它自纠
- [ ] 上下文超限时你裁什么、保什么，依据是什么
- [ ] 你的 agent 成功率是多少、怎么算的、评测集有多少条
- [ ] 一次 run 平均多少轮、多少 token、多少钱；贵在哪一步
- [ ] 说清你会在哪一步拒绝让模型自主决策、为什么

## 10. 简历上这个项目怎么写

```
• 基于 Go 从零实现 agent runtime：感知/规则判断/写回三层解耦，LLM 仅替换决策层，
  通过 function calling 驱动工具循环至收敛
• 设计评测集 N 条 + trace 回放，agent 任务成功率从 X% 提升到 Y%，
  平均轮次从 A 降到 B
• 定位并修复 agent 死循环/工具幻觉/上下文溢出等问题，输出踩坑复盘 N 篇
```

（把 X/Y/A/B/N 换成真实数字——这也是为什么评测（s6）必须在讲结果之前完成。）

## 一句话收尾

和隧道线同一个标准：**别用「用过什么框架」衡量成长，用「今年能不能让一个不靠谱的 agent 变得靠谱」**。
模型每三个月翻新一次，你写的循环控制、工具协议、评测体系——三年后还是你的。
