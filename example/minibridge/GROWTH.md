# 进阶路线：从"能造出一个组件"到"能负责一个领域"

配套 TODO 池（TODO.md）。这份管两件事：**这批能力在市场上值多少**，以及**再往上往哪走**。

---

## 0. 最重要的一条方法论（先记住这个）

> 面试考的是「为什么这么设计、踩过什么坑、怎么权衡」，不是「能不能写出来」。
> 把每个 TODO 都能讲成一个故事（现象 → 定位 → 方案 → 权衡），价值远大于悄悄做完。

### 故事模板（每个功能都用这个格式讲）

```
功能：<名字>
现象：<线上/测试里看到什么异常>
定位：<怎么查到的 —— 用了什么命令、看了什么日志/抓包>
方案：<怎么改的>
权衡：<为什么选它、放弃了什么、代价是什么>
数据：<验收数字，拿数字说话>
```

### 现成的故事素材（已经真实发生过的故障）

| 故障 | 可讲的点 |
|---|---|
| 空闲约 10 分钟被掐断 | NAT/安全组 idle 回收；长连接保活；半开连接为什么 TCP 层发现不了 |
| 僵尸会话刷 `open stream timeout` | 没有心跳就发现不了死连接；要不要重连；失败后该退出还是重试 |
| `srv.crt` SAN 与 `-server` 地址不匹配 | Go 早就不认 CN；SAN 是什么；为什么用 IP 连时 Go 不发 SNI |
| 端口上不是 TLS 服务（`packet length too long`） | 协议识别与误连处理；`0.0.0.0` vs `127.0.0.1` 绑定差异 |
| 服务端 dial 出大量 `FIN-WAIT-2` / `CLOSE-WAIT` | 半关闭穿透；对端不关会怎样；怎么定位到进程和 fd |

## 1. 这批能力的画像

> 能独立交付一个带安全模型的网络中间件：协议设计 → 密码学选型 → 上线运维 → 排障压测，全流程自己扛。

这不是"会用框架写业务"那一层，是**基础设施/中间件方向的中高级工程师**。

## 2. 含金量分布不均（很重要）

| 值钱（面试真加分） | 不太值钱（加分有限） |
|---|---|
| 协议设计：多路复用、流控/背压、生命周期 | 某个 API 怎么调（怎么做证书、怎么写 systemd unit） |
| 排障能力：TCP 状态机、抓包定位、半开连接 | 工具熟练度本身 |
| 权衡能力：mTLS 为何优于应用层认证、何时该用现成的 | 功能实现得多 |
| 线上意识：优雅退出、可观测、限流、吊销 | 代码量 |

## 3. 职级映射（粗对齐，各厂口径不同）

| 厂 | 大致档位 |
|---|---|
| 阿里 | P6 稳 / 摸 P7 边 |
| 字节 | 2-1 / 2-2 |
| 腾讯 | 8~9 级 |

分水岭在 **P7 / 2-2**：要的不是"能独立做"，而是**能在别人的系统上做设计决策、带人、扛线上事故**。

## 4. 薪资（2024-2026 中国，税前年包，粗区间）

| 档 | 一线（北上广深杭） | 二线 |
|---|---|---|
| P6 / 2-1 高级 | 约 35–55 万 | 打 7–8 折 |
| P7 / 2-2 资深 | 约 55–85 万 | 同上折 |
| P8 / 2-3 往上 | 85 万+，含股票浮动大 | — |

**别拿这些数字当准数：**

1. 行情波动大，赛道差异能拉开 30% 以上（AI / 基础设施热，传统业务冷）
2. 年包口径混乱：股票按什么价折、签字费、公积金比例，差很多
3. 决定薪资的不只是技术：城市、公司规模、学历、年限、面试当场表现、业务稀缺性、能不能带人
4. 真实数字去看脉脉 / OfferShow / levels.fyi，筛同城同档同赛道、看近半年

### 一个容易忽略的点：稀缺性是相对的

同一套能力——

- 放在全体工程师里：你是少数
- 放在大厂基础架构团队里：这是基本功（旁边的人天天在做）

**选战场比多学一点技术更能改变定价。** 去需要它的团队（中小厂、创业公司、云原生/安全/中间件团队），它就是核心资产。

## 5. 从"掌握池子"到"那个级别"差三件事

1. **规模**：自己写的跑 3 条流 vs 线上跑 3 万条流，是两种工程。要有"在真实量级上扛过"的经历
2. **协作**：在别人的代码库里改、写设计文档、被 review、说服别人——独立项目练不到
3. **事故**：能讲出"线上出过什么事故、怎么定位、怎么止损、怎么防复发"，P7 面试里权重极高

> 结论有点反直觉：**做完池子不会自动让你到那个级别，但它给了你讲出那些故事的素材。**

## 6. 坐标：用"能解决什么层级的问题"丈量，别用级别

| 层 | 能解决什么 | 现状 |
|---|---|---|
| L1 | 用工具、改配置 | 已过 |
| L2 | 在别人的系统里改代码 | 已过 |
| L3 | **独立设计一个组件并让它在线上跑** | **当前位置** |
| L4 | 设计一个系统（多组件、一致性、容灾），对稳定性负责 | 下一站 |
| L5 | 定义一个领域该做什么/不做什么，对业务结果负责 | P7/P8 |
| L6 | 影响团队/公司甚至行业的技术方向 | P8+ |

## 7. 再往上的四条路

**① 深度：从"能跑"到"扛得住量"**
并发模型、内存与 GC、尾延迟、真流控与背压、零拷贝。产物是**数据**：iperf3 对比、pprof 火焰图、24h 长跑的 fd/goroutine 曲线。能量化系统边界是 L4 的硬指标。

**② 系统：从"一个组件"到"一个系统"**
多实例协同（一致性/选主/Raft）、容错、水平扩展、多租户隔离、可观测体系。经典跃迁是**实现一个带复制的 mini 分布式 KV**——它逼你面对"部分失败"，那是单进程里永远遇不到的难题。

**③ 决策：从"我做"到"我们做"**
写设计文档、过评审、在别人代码库里改、被 review。**最快练法：给成熟开源项目提 PR**（修 bug 也行），这是唯一能低成本获得"在别人系统上改代码并被专业 review"的训练。

**④ 杠杆：从"技术"到"结果"**
你做的东西给谁省了什么、省了多少、为什么现在必须做、不做什么。P7 与 P8 的分界不在技术深度，在**能否对一个领域的结果负责，并让别人愿意跟着你做**。

## 8. 见效最快的两件事

1. **把当前项目平台化**：补文档、systemd 部署、压测报告、故障复盘（NAT 断线那次写成一篇）。有数据、有复盘、能被别人直接用，比十个 demo 有力，且直接体现 L4 思维
2. **给真实开源项目提 3 个 PR**：同时练第③④条，也是简历上"能在别人系统上协作"最硬的证据

## 10. 职场晋升：技术之外的那一半

技术是入场券，晋升是另一套游戏。这一节跟技术无关，但决定你能不能拿到那个级别。

### 10.1 晋升的真实机制

晋升不是"技术达标就升"，而是三个条件同时成立：

1. **业绩**：做过什么，有可量化的结果
2. **影响力半径**：超出自己那一亩三分地（跨团队、带人、沉淀方法论）
3. **可信度**：有没有人愿意在评审会上为你背书

评审的本质是：**一群不熟你工作的人，在半小时内通过你的材料和背书人的话，判断"他是不是已经在干下一级的活"**。

所以唯一正确的姿势是——**先做下一级的事，再拿下一级的级别**，不是反过来。等你"被提升到那个位置再学"就晚了。

### 10.2 评审通用维度（各家大同小异）

| 维度 | 评审实际在看什么 |
|---|---|
| 复杂度 | 解决的问题有多难、有没有技术深度 |
| 独立性 | 是你自己扛下来的，还是被人带着做的 |
| 影响力 | 影响自己 / 团队 / 跨团队 / 公司 |
| 结果 | 对业务的可量化贡献（不是工作量） |
| 协作与带人 | 能不能让别人也做成（P7 的分水岭） |

注意"结果"那一栏：评审问的是**业务结果**，不是"我写了多少代码、实现了多少功能"。

### 10.3 能见度（技术人最容易丢分的一项）

> "我做完了" ≠ "别人知道我做完了"。

做的事必须留下**可被检索的证据**：

- 设计文档（评审前写，评审后归档）
- 故障复盘文档（最值钱的素材）
- 组内技术分享（每月一次，成本极低）
- 代码 review 记录、方案讨论记录
- 周报里写"决策与结果"，不是"本周做了啥"

### 10.4 向上管理

- 定期 1:1 对齐目标，别等绩效面谈才知道期望
- 直接问清楚：**"升到下一级，我需要做出什么？"** —— 这句话要问出口
- 主动要"下一级的活"："这块设计我想试着负责，行不行？"
- 进度主动同步，别让 leader 来问

### 10.5 跨团队与背书

晋升需要背书人，而背书是平时攒的：

- 帮别的团队解决过问题 = 关键时刻有人替你说话
- 主动接"没人愿意做但重要"的活（稳定性专项、工具链、文档体系）—— 这类活容易被看见，也最容易出数字
- 跨团队项目里留下你的名字和产出

### 10.6 带人：从"我做"到"通过别人做成"

这是 P6 → P7 真正的分水岭：

- 带新人/实习生、做 code review、把经验沉淀成文档让别人能上手
- **能复制自己 = 有杠杆**。一个人扛完所有活，反而说明你还在上一级
- 把"我解决了"变成"我们团队现在都能解决"

### 10.7 把 §5 那"差的三件事"变成真经历

| 缺的 | 怎么补（落地打法） | 证据形态 |
|---|---|---|
| **规模** | 主动认领线上系统的性能/稳定性专项 | before/after 数字：QPS、P99、资源占用 |
| **协作** | 给开源项目提 PR；参与跨团队项目；主动 review 别人的代码 | PR 链接、评审意见、跨团队项目产出 |
| **事故** | 主动进 oncall/值班；**每次故障写复盘**并跟进防复发项落地 | 复盘文档：止损时间线 / 根因 / 改进项 / 闭环结果 |

**复盘是最值钱的晋升素材**：它同时证明复杂度、独立性、结果三项，而且是别人抢不走的真实经历。

### 10.8 述职材料怎么写

结构（每个项目都用这个）：

```
背景与问题：  <为什么要做，不做的代价>
我做了什么：  <关键决策点，不讲流程>
结果：        <数字，必须有对比基线>
影响半径：    <自己 / 团队 / 跨团队 / 公司>
沉淀：        <复盘、文档、是否可复用>
```

三条铁律：

1. **讲决策，不讲流程**——"我权衡了 A/B，选了 A 因为…" 比 "我先做了 X 再做 Y" 有力十倍
2. **讲结果，不讲工作量**——配一个数字：延迟降了多少、故障次数降了多少、省了多少机器
3. **讲"我"，但要诚实**——说清你的部分，别把团队成果揽上身

常见翻车点：需求列表式罗列、技术细节堆砌、没有对比基线、把"我们"说成"我"。

### 10.9 简历上这个项目怎么写

三条 bullet 就够（按上面模板）：

```
• 设计并实现基于 TLS 1.3 双向认证的多路复用 TCP 隧道（Go），端口级目标白名单收敛 SSRF 面，
  已部署于生产环境承载远程开发链路
• 定位并修复长连接空闲被中间设备回收导致的会话僵死：引入应用层心跳与重连，
  故障恢复时间从"需人工重启"降到 X 秒
• 通过 tcpdump/SSLKEYLOGFILE 与连接状态分析定位跨主机转发故障 N 起，输出复盘文档 X 篇
```

（把 X 换成真实数字，别空着。）

### 10.10 常见误区

1. 闷头做技术，等别人发现 → 要做能见度
2. 只挑难度高的做，不关心结果 → 评审看结果
3. 什么都自己扛 → 到 P7 必须有杠杆
4. 只跟自己 leader 打交道 → 需要跨团队背书
5. 绩效材料临时凑 → 平时就要留证据

### 10.11 晋升自检清单

- [ ] 能说出"升到下一级，我需要做出什么"（且跟 leader 对齐过）
- [ ] 至少有一份**带数字**的线上结果（before/after 明确）
- [ ] 至少写过一篇故障复盘，且改进项已闭环
- [ ] 至少有一次跨团队产出，有人能为你背书
- [ ] 有带人/帮别人上手的实例（review、文档、带新人）
- [ ] 做过至少一次组内分享
- [ ] 有一个"成果台账"，随时能拿出来写材料
- [ ] 做过一次模拟答辩，被人挑过刺

### 10.12 行动清单（低成本，可立刻开始）

| 频率 | 动作 |
|---|---|
| 每次故障 | 写复盘（止损时间线 / 根因 / 防复发项） |
| 每月 | 一次组内技术分享 |
| 每两周 | 与 leader 1:1 对齐目标与期望 |
| 每季度 | 认领一件跨团队事项 |
| 持续 | 维护"成果台账"：时间 / 事项 / 数字 / 证据链接 |
| 每半年 | 做一次晋升模拟答辩，找同级或上级挑刺 |
| 一次性 | 给开源项目提 3 个 PR；带一个新人 |

### 10.13 成果台账模板

```markdown
| 时间 | 事项 | 我的角色 | 结果（数字） | 影响半径 | 证据链接 |
|---|---|---|---|---|---|
| 2026-10 | 隧道长连接僵死修复 | 独立设计+实施 | 恢复时间 → Xs | 团队 | docs/postmortem-xxx.md |
```

平时顺手填，半年后写材料只要十分钟。

### 10.14 几句实话

- 晋升还要看**坑位与组织需要**：能力到位但没坑，是常态
- 别把晋升当唯一目标。**能力到位后市场会给价**，有时跳槽比等内部坑位快
- 内部晋升拼"证据 + 背书"，外部跳槽拼"能讲出什么故事"——两者都靠平时积累，不靠临场发挥
